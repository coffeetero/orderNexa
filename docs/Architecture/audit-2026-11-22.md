## Navigation redesign (done)

Sidebar replaced by a sticky top bar (`components/layout/TopNav.tsx`): Radix menubar dropdowns on desktop
(grouped, two columns for menus with 3+ groups), a left drawer with accordion groups below 1024px, user menu
at the right (Profile, Account Settings, Back to Site, Logout). Used by both the staff shell and the customer
portal. Menus live in `lib/nav-config.ts`; entries without a page are shown greyed as "Soon" instead of
linking to a 404 (`nav-config.test.ts` fails if a `soon` flag is stale). A branded `app/not-found.tsx`
replaces the bare Next.js 404. Removed `TenantSidebar`, `CustomerSidebar`, `DashboardHeader` and the
breadcrumb strip (the active menu is highlighted instead). The customer header now shows the real user and
account instead of "Marie Dupont / Le Jardin Restaurant". Search, Notifications and the Notification
Preferences / Security / Help menu entries were inert before and remain placeholders (the latter three
now marked "Soon").

## Route crawl (done)

Every nav link, user-menu target and key dynamic route was requested as staff, customer and anonymous
against the dev server and the production build (63 requests per host). On a tenant host
(`alpine-bakery.localhost:3000`) there are no failures; unbuilt "Soon" pages 404 as intended and the guards
redirect correctly (customer on staff URL / other slug -> own portal, logged out -> /login).

Bug found and fixed: on bare hosts (`localhost`, `127.0.0.1`) the middleware only rewrote staff URLs
(`/dashboard`, `/orders`, …) on tenant subdomains, so login -> `/dashboard` 404ed. The rules now live in
`lib/tenant-routing.ts` (unit-tested) and apply on bare hosts too; staff pages get their tenant from the JWT,
not the host. By design the customer portal still needs a tenant host, so a customer signing in on a bare host
now gets an explanatory message instead of a 404.

Known quirk (unchanged): "Back to Site" for a signed-in staff user on a tenant host goes to `/`, which redirects
to `/dashboard`; the public site is only visible when signed out.

## Breadcrumbs and contextual sidebar (done)

Breadcrumb strip under the top bar (`Module › Page › Record`, from `lib/nav-config.ts` + the page's current
record) and a 260px sidebar: **Quick access** (3 actions per user: pinned first, then most used in the last 90
days, then defaults Enter Orders / Customer Profiles / Item Profiles — Item Profiles stands in until Manage Items
exists) and **recent records** per module (Customers: customers; Orders: customers + orders; Inventory: items;
Production: runs, no source yet). Docked at >=1280px (hide/show remembered in the `bps_sidebar` cookie), a drawer
below that.

- Data: `fnd_user_menu_actions` (per user, not tenant) and `fnd_user_recent_records` (per user + tenant, 20 per
  type), RLS on, owner-only; functions `fnd_nav_touch`, `fnd_nav_sidebar_get`, `fnd_nav_pins_set`; API
  `/api/nav/{sidebar,touch,pins}`. Files are under `database/{schema,policies,functions}`; the cloud migration is
  `database/migration/add_user_nav_tracking.sql` (NOT applied to the cloud). SQL tests:
  `database/tests/nav_tracking_test.sql` (rolled back, local only).
- Pages report their record with `useCurrentRecord` / `useBreadcrumbRecord` / `useTrackRecent`, register
  unsaved-changes checks with `useNavGuard`, and accept `?customer=` / `?item=` through `useDeepLinkId`, which feeds
  the page's existing selection handler. `EntityComboBox` / `OrderHeaderRow` were not changed.
- A shared guard asks before the sidebar, breadcrumbs or the top menu discard an edited order, customer or item
  (Enter Orders compares against a snapshot taken when the order is loaded or saved).

Related fix: the customer layout read `user.app_metadata.app_user_id`, but `auth.getUser()` does not contain the
access-token hook's claims (they are only in the JWT), so `fnd_session_get_timeout` was never called. It now uses
`fnd_users.user_id`.

## Open — security (deferred by request; see also the earlier credential cleanup)

- 24 tables in `bps` have **RLS off** while `anon`/`authenticated` hold broad grants, including
  `fnd_users`, `fnd_customers`, `fnd_user_customers`, `ordr`, `ar`, `item`… Anyone with the public anon key can
  read them. The same is true in the cloud project.
- `fnd_customers_get_v2`, `fnd_items_profile_*`, `om_items_get_v2`, `om_orders_*` are `SECURITY INVOKER` and take
  `p_tenant_id` from the client; with no RLS on `fnd_customers`, tenant isolation there depends on the caller.
- `pol_fnd_users_tenant` / `pol_fnd_user_customers_tenant` exist but RLS is disabled, and they key on
  `app_metadata.tenant_id`, which the access-token hook does not emit (it emits `allowed_tenant_ids`). Enabling RLS
  as-is would lock everyone out.
- Stray tables `v_allowed_tenant_ids`, `v_app_user_id`, `v_restricted_tenant_ids`, `v_result`, `v_tenant_id` look
  like accidental `SELECT … INTO` artifacts and are readable by anon.
- `docs/Supabase/connections.md` is committed with database passwords (public repo).
